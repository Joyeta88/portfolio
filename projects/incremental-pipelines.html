Semantic medallion pipelines for customer journey analytics

Replaced daily full-season table rebuilds with an incremental, layered lakehouse design—cutting end-to-end runtime by roughly 6–10× while preserving funnel and conversion metrics that leadership relies on for season-close reporting.

How AI was used end to end

This was not “AI wrote SQL and we shipped it.” AI accelerated every phase of the lifecycle while deterministic checks stayed in control:

  • Develop — Pair-programmed incremental SQL (layered MERGE, changed-user detection, orchestration) in an agentic IDE; iterated on partition strategy, dedupe keys, and aggregate grain with rapid test cycles on the warehouse.
  • Align — Generated validation memos, architecture diagrams, and stakeholder-facing summaries so analytics, product, and finance could agree on what “match to legacy” meant before production.
  • Validate — Built repeatable test-vs-production comparison queries and edge-case playbooks (lookback boundaries, late arrivals, asymmetric dimension joins); used AI to document root causes when deltas appeared.
  • Monitor — Codified monitoring thresholds (daily user volume, step-level funnel counts, runtime per layer) and runbooks for extended lookback after upstream delays.

The result was faster iteration without sacrificing auditability—every anomaly was traced to when data landed or when identity mappings updated, not silent logic drift.

Problem: full reloads at seasonal scale

The legacy pattern dropped and recreated entire seasonal clickstream and journey-aggregate tables every morning. Each run re-scanned 100+ days of raw event partitions and re-computed aggregates for the full active population—even when only a small fraction had new activity overnight.

That approach was simple but expensive: long runtimes during peak season, unnecessary compute, and fragile timing when raw events or identity bridges arrived after the morning rebuild.

Solution: semantic medallion layers + incremental processing

I designed a multi-layer medallion architecture where each stage has a clear semantic contract. Downstream metrics consume governed layers—not raw events—so funnel definitions stay stable even when ingestion is incremental.

Layer 1 — MERGE instead of drop/recreate

The bronze layer uses MERGE into a persistent table: only the last N days of load partitions are read from source, and rows upsert on a natural key (customer, event time, screen, load partition). Re-runs are safe—duplicate inserts are prevented.

This replaced the anti-pattern of dropping a season-wide table and hoping the morning job finishes before downstream consumers refresh.

Lookback window design

I ran a formal lookback study comparing 2-day vs 7-day ingestion windows on billions of events:

Window Events captured Relative runtime
2 days (chosen) ~99.99% of volume Baseline (~60 min estimated full stack)
7 days ~99.9999% (+0.01% gain) ~2.5–3× longer — rejected

The remaining ~0.01% of events arriving more than two days late are still captured on a later run because MERGE is idempotent—no need to widen the window and pay a 3× compute penalty every day. For upstream outages beyond two days, a one-time extended lookback backfill is documented.

Layer 2+ — Targeted re-aggregation (not full recompute)

Higher layers identify customers with new bronze activity, delete only their stale aggregate rows, and re-insert fresh journey features. On a typical mid-season day that is on the <1% of the daily active population—roughly 125× less work than a full rebuild.

Deeper layers apply FULL OUTER JOIN patterns where two asynchronous sources (behavioral events vs transactional outcomes) can arrive in either order, so funnel completeness does not depend on which source lands first.

Customer journey touchpoints in metric definitions

A core design goal was that metric definitions encode the journey, not just counts from a wide event table. Silver and gold layers materialize explicit touchpoints—for example:

  • Early journey: entry screens and option discovery
  • Mid journey: consent, disclosure, and policy acceptance
  • Late journey: selection, confirmation, and outcome alignment

Platinum aggregates expose these as daily funnel steps so product and finance see the same progression. Validation focused on conversion-critical steps (legal consent, terms, commitment events)—those showed zero delta vs legacy on settled dates. Top-of-funnel view counts showed small negative deltas when identity bridges updated between runs; that behavior was documented and expected under incremental scheduling.

Last-touch ranking (e.g., which option was selected most recently) can temporarily lag if a late event arrives; subsequent daily runs self-correct—another reason MERGE + incremental re-aggregation beats one-shot full reloads.

Late-arriving clickstream data

Late arrival is normal in high-volume behavioral pipelines: batch boundaries, timezone alignment, and upstream load delays mean “event day” and “land day” diverge for a meaningful share of traffic (~27% landing one day after the user action in my lag study).

The operating model has three parts:

  1. Overlapping lookback — Each daily run re-reads two load partitions so yesterday’s late landers are merged into bronze.
  2. MERGE idempotency — Events that appear three or more days late are picked up when their partition finally lands—no silent drop.
  3. Interpretation of positive deltas — When incremental runs later in the day than legacy morning rebuilds, same-day counts can be higher—that is completeness improving, not a bug. Both validation phases showed this pattern on the freshest date.

Validation & monitoring

Phase 1 — Full-season backfill

Seeded test tables with a one-time seasonal backfill, then compared 30 consecutive reporting days. Historical dates landed within tight user-volume tolerance (<0.05%) with conversion steps matching exactly.

Phase 2 — True daily incremental

Ran the production orchestration (MERGE → delete changed users → insert fresh aggregates) against those test tables. Measured layer timings: ~4.3 min bronze MERGE, ~1 min silver/gold refresh, ~5.5 min total. Fifteen-day funnel comparison replicated the same delta story.

Role & stack

Role: Lead analytics engineer — architecture, SQL, validation design, production readiness, and stakeholder sign-off.
Stack: Lakehouse SQL warehouse, Delta-style tables, orchestrated ELT jobs, Python runner for statement execution, agentic IDE for development and documentation.

What I’d tell another team

  • Invest in semantic layers before incrementalizing—otherwise you incrementally reload chaos.
  • Prefer MERGE + narrow lookback over widening windows; let idempotency handle the long tail.
  • Validate funnel steps that matter for decisions, not only top-line user counts.
  • Use AI for speed of iteration and explanation, not as the source of truth for metrics.
