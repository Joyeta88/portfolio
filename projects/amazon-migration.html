Enterprise BI · Medallion Architecture · KPI Governance

Healthcare analytics migration: third-party stack to governed first-party platform

Co-authored the target architecture for an enterprise Operations Data Studio—migrating analytics off a third-party warehouse and visualization stack onto a first-party AWS lakehouse with medallion layers, standardized KPI datasets, and a governance model serving 11+ partner teams.

Medallion Migration KPI Governance S3 · Spark · Glue Redshift · Athena

Impact at a glance

200+ Dashboards migrated to governed datasets
500+ Standardized KPIs in the enterprise catalog
700+ Datasets brought under platform standards
11+ Partner teams on shared definitions & layers

Outcome: One system of record for operations analytics—raw history preserved, normalized entities reusable, gold-layer datasets optimized for reporting. Retired hundreds of redundant pipelines while cutting platform cost and improving trust in leadership metrics.

The problem

Healthcare operations analytics had grown through years of federated extracts, vendor-hosted warehouses, and team-specific logic. Dashboards diverged, refreshes were fragile, and third-party tooling made cost and access hard to govern. Partner teams needed the same operational truth without each building their own path from raw systems to slides.

Design approach

BI and data engineering leadership aligned on four design commitments (documented in the platform architecture specification):

  1. Build once, reuse often — Compose larger capabilities from small, independently maintainable pipelines instead of monolithic one-off jobs.
  2. Quality over speed — Production changes pass code review; favor durable solutions over quick fixes that break at scale.
  3. Right-sized serverless processing — Batch and streaming workloads on managed Spark with minimal operational overhead.
  4. Prepare for change — Modular layers so new sources, volume spikes, and org restructuring do not require greenfield rebuilds.

Medallion architecture

The platform follows a classic bronze → silver → gold medallion pattern: progressively refined data with clear contracts between layers. Authorized consumers access the layer that matches their need—lineage at the bottom, performance at the top.

Bronze (raw zone)

  • Ingest from first-party operational systems, internal services, and approved third-party file feeds
  • Preserve historical, append-friendly archives for audit and reprocessing
  • Land in columnar object storage; register in the enterprise metadata catalog without unnecessary data movement

Silver (normalized zone)

  • Cleanse sensitive fields; deduplicate on stable entity keys
  • Model core business entities and events in normalized form (operations, fulfillment, orders, logistics—conceptually)
  • Serve ad hoc analysts, ML, and downstream engineering—not executive dashboards directly

Gold (analytics zone)

Two governed flavors—this is the KPI medallion extension on top of classic medallion:

  • Denormalized / BI datasets — Subject-area tables with joins and business rules applied once; optimized for read patterns and BI tools
  • Metric datasets — Daily-grain aggregates with standard dimension slices across subject areas; feed weekly business reviews and executive reporting

Hard rule: Metric datasets are built only from gold denormalized tables—never directly from silver—so upstream schema changes do not silently break leadership KPIs.

Migration: third-party to first-party

The program moved consumption from a third-party columnar warehouse and embedded BI product to a first-party stack: object storage, catalog, serverless Spark, Glue-class orchestration, interactive SQL on the lake, and a clustered warehouse for heavy analytics.

Dimension Before After
System of record Fragmented extracts + vendor warehouse Operations Data Studio medallion platform
Dataset standards Team-by-team conventions Templates for silver, denorm, and metric tables
KPI lineage Often embedded in dashboard logic Metadata catalog + unified metric process
Operational cost High vendor licensing footprint Material annual savings (pay-for-use processing)
Retired complexity Overlapping ETL and unused jobs 400+ legacy pipelines decommissioned

Quality standards & governance

Standards were as important as the technology choice:

  • Architecture templates — Standard designs for normalized tables, denormalized datasets, and metric datasets; designs reviewed and stored in a shared repository
  • Code review on production paths — No ad hoc pushes; CI/CD deploys to production accounts
  • Unified metric metadata — KPI meaning, grain, and refresh documented in a catalog table consumed by analytics and BI
  • Partitioning & keys — Silver optimized for entity integrity; gold optimized for partition pruning and predictable query cost
  • Proactive monitoring — Pipeline health and freshness surfaced before stakeholder-facing reviews break
  • Access & ownership matrix — Layer-specific ownership (raw vs normalized vs reporting) with LDAP-style group access for SQL clients and dashboards

Technologies adopted

The platform was built on a standard AWS analytics stack—each service had a clear job in the medallion flow, not overlapping responsibilities. Below is how the team used them in practice.

Technology Role on the platform Typical layer / consumer
Amazon S3 Central object store for columnar files (e.g. Parquet); durable bronze archive and shared handoff between federated BI teams Bronze · cross-team sharing
Apache Spark (managed) Primary compute for dedupe, typing, joins, and business logic across bronze → silver → gold; SQL, Python, or Scala jobs with minimal cluster ops Silver · Gold processing
AWS Glue Data Catalog System of record for table schemas, job definitions, partition metadata, and schema version history All layers (metadata)
AWS Glue Crawlers Infer schemas on new landings, register partitions, keep catalog in sync—often triggered when objects arrive in S3 Bronze · Silver registration
AWS Glue ETL Managed jobs to prepare, transform, and load datasets where visual ETL or standardized job patterns fit Silver · Gold
Amazon Athena Serverless SQL over open files in S3 for exploration, validation, and lightweight ad hoc analysis—pay per query Bronze · Silver (analysts)
Amazon Redshift Columnar MPP warehouse for heavy joins, large history, and performance-sensitive reporting workloads Gold · BI consumption
CI/CD pipelines Version-controlled job code, mandatory review before production, automated deploys to approved accounts—reduced manual release errors All pipeline code
Cloud BI & SQL clients Executive dashboards and analyst workbench access pointed at gold-layer datasets and governed metric tables Gold · Metric layer
AWS Lake Formation Centralized permissions and data-lake governance across catalogs and consumers where teams publish and subscribe Platform-wide access

How this supported migration

  • S3 + Spark replaced vendor-hosted storage and transform patterns with an internal, pay-for-use model and clearer cost attribution per pipeline.
  • Glue Crawlers + Catalog made new bronze landings discoverable quickly without manual schema documentation drift.
  • Athena let teams validate migrations and debug layer logic before pointing dashboards at Redshift or BI.
  • Redshift + BI became the consumption tier for gold and metric datasets—aligned with the rule that leadership KPIs never read silver directly.
  • CI/CD turned pipeline changes into the same discipline as application software—critical when 11+ teams depended on the same platform.

My role

As a BI manager on the data foundations team, I co-led the architecture specification with peer BI/DE managers, aligned 11+ partner teams on layer contracts, and drove migration execution with a 15+ person analytics organization—dashboard moves, KPI harmonization, pipeline retirement, and field enablement on the new platform.

What I’d tell another enterprise

  • Medallion only works if gold metric rules are explicit—protect KPIs from raw churn.
  • Templates and review gates scale better than hero pipelines.
  • Migration is a governance program, not a lift-and-shift of SQL.
  • Partner teams adopt when they see the same number in the meeting and in the catalog.
