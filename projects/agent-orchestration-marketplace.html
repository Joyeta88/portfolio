Orchestrated agents on a governed skills marketplace

Designed a two-layer agent system for a large analytics organization: a shared marketplace that packages rules, skills, and plugins for two IDEs, plus domain orchestrators that coordinate specialized worker agents for end-to-end analysis—without letting LLMs improvise metrics or steps.

Rules Skills Plugins Orchestrator Contributor factory

Impact at a glance

2 IDEs One marketplace source → Cursor rules/skills + Claude plugins
Coordinator Orchestrator skill routes complex asks to task specialists
Factory loop Contribute → review → pull/push for team-wide sync
Guardrails Thin always-on rules; heavy logic in on-demand skills

Outcome: Analysts invoke one entry point for multi-step workflows; platform maintainers ship capabilities once and sync everywhere. Agents coordinate each other through skills and explicit dispatch, not ad-hoc prompt chains—and humans stay in the loop for publication and dedup.

Part B — The marketplace factory

A central open-market repo is the single source of truth. Content flows differently per IDE, but authors edit one place.

Rules vs skills vs plugins

ArtifactRoleWhen it loads
Rule (.mdc) Short guardrail—git hygiene, link routing, SQL orchestrator trigger Automatic when alwaysApply: true (keep count small—token cost)
Skill (SKILL.md) Multi-step workflow—test read, pipeline setup, marketplace push On demand via @skill-name in Cursor (not slash picker)

Contributor lifecycle skills

Agents follow the same factory skills humans use—meta-workflow, not magic:

  • Contribute — scaffold a new skill locally, test triggers, avoid duplicating existing coverage.
  • Review — audit conflicts, redundant always-on rules, and context-window budget.
  • Push — scan changes, open branch and PR to the marketplace.
  • Pull — sync latest rules/skills to the analyst machine after merge.

Design principle: Edit skills/ in the repo, never generated plugin copies. Regenerate Claude bundles from source so Cursor and Claude Code stay aligned.

Part C — Domain orchestrator (coordinator + workers)

For a complex domain (e.g., paid media, CRM, or multi-product monetization), a single monolithic skill becomes unmaintainable. Instead, a coordinator orchestrator skill sits above a dozen task skills and decides what to run.

When the orchestrator runs vs direct routing

User askRoute
“Weekly channel performance” (multi-surface)Orchestrator → several workers + synthesis
“Run the budget allocator only”Direct to single task skill
“Why did yesterday’s pipeline fail?”Direct to debugging skill
“Onboard me to this domain”Direct to onboarding skill

Orchestrator phases (generic)

  1. Freshness — confirm warehouse tables cover the requested window (spend vs traffic lag differs).
  2. Intent parse — map question to task skills; skip orchestration for single-skill asks.
  3. Parallel dispatch — invoke workers (sub-agents or sequential skill blocks) with shared date grain.
  4. Cross-validation — reconcile spend, impressions, or funnel totals across worker outputs.
  5. Synthesis — one narrative; route to output skill (slides, formatted chat, HTML brief).

Agents building agents (with human gates)

“Agents building agents” here means structured delegation, not autonomous self-replication:

  • Parent session loads orchestrator → delegates to worker skills (each SKILL.md is an agent contract).
  • Skill-lifecycle intake runs before new skills—dedup scan across three layers (name, triggers, description).
  • Explore subagents (read-only) can search the codebase for overlap; parent merges findings into one skill package.
  • Humans approve PRs to the marketplace—no bypass-permission agent files in the discovery path.

How this pairs with deterministic analytics

Orchestrators handle workflow; separate cascade skills (e.g., SQL orchestrator) handle metric truth: classify intent → resolve contracts → validate dimensions → execute warehouse query. LLM speed sits on top of deterministic guardrails—not instead of them.

Lessons (portable)

  • Few always-on rules. Every token hits every chat—push procedures into skills.
  • @ not / in Cursor. Slash picker may not load full SKILL.md; workers hallucinate steps.
  • One orchestrator per domain. Avoid N×N routing between task skills and output formats.
  • QA between workers. Parallel agents drift on date grain—reconcile before synthesis.
  • Marketplace before maverick prompts. If you correct the same thing twice, publish a skill.
  • Generated plugins are read-only. Always edit source skills and rebuild bundles.
